# qdrop threat model

## What qdrop is

A LAN-only bridge between a small, fixed set of devices **you own**. It syncs
clipboard text/images, sends files, and pushes URLs. There is no server, no
account, and no internet relay.

## Assets

- **Clipboard contents** — often sensitive (tokens, addresses, snippets).
- **Files** sent via `qdrop send`.
- **The long-term identity key** (`~/.config/qdrop/identity.pem`).
- **Availability** — the daemon should not be a local DoS vector or a way to
  write arbitrary files.

## Trust model

- Devices are paired **once**, out of band, via a 6-digit PIN. After that each
  device knows the other's Ed25519 public key and trusts nothing else.
- The local user and anything running as them is fully trusted (it can read the
  clipboard and the key directly anyway).
- Everything on the wire is untrusted.

## Adversaries and mitigations

### Passive network eavesdropper (same LAN / Wi-Fi)

Sees mDNS records (device names, ports, key fingerprints) but **not** payload:
the steady-state transport is TLS 1.3 with a modern AEAD suite
(`ring` provider). mDNS TXT deliberately carries only non-secret metadata.

### Active man-in-the-middle

- **During pairing:** SPAKE2 is a PAKE — without the PIN an attacker cannot
  derive the session key, and the identity exchange is authenticated with an
  HMAC over the SPAKE2 secret plus a mutual confirmation byte. A wrong PIN or a
  flipped byte makes the HMAC check fail and pairing aborts before anything is
  trusted. The PIN is 6 digits (~20 bits); SPAKE2 gives one online guess per
  attempt and the offer window is 60 s, so brute force is impractical.
- **Steady state:** the TLS verifier pins the peer's **raw Ed25519 key**
  (`tls::peer_key_from_cert`) — no CA, no name check, no trust-on-first-use.
  The handshake signature is still verified against that key, so presenting a
  copied certificate does not help. Both directions are authenticated
  (mutual TLS); a connection from an unpinned key is refused mid-handshake.

### Malicious paired peer (or a compromised one)

A paired device is trusted to send you clipboard data, files, and URLs. Blast
radius is limited:

- **Files:** the name is sanitised on receipt (`safe_blob_name` rejects
  separators, `..`, absolute paths, drive/UNC prefixes) and written only under
  `~/Downloads/qdrop/`. SHA-256 and the declared size are verified before an
  atomic rename; a mismatch deletes the temp file. `require_confirm = true`
  diverts everything to `~/Downloads/qdrop/pending/`.
- **URLs:** `is_allowed_url` permits only `http` / `https` / `mailto`, rejects
  control/whitespace/quote characters, and the URL is passed to `open` /
  `xdg-open` as a single argv element — never through a shell. `file:`,
  `javascript:`, `data:` are refused on both ends.
- **Clipboard:** size-capped (`max_clipboard_bytes` for text, 64 MiB for image
  blobs) and rate-limited. Images are always re-encoded to PNG.
- The peer **cannot** run commands, read arbitrary files, or escape the
  download directory.

### Local denial of service

- Frames are length-prefixed with a hard 16 MiB cap; oversize prefixes are
  rejected without allocating.
- One blob in flight per connection; in-memory (clipboard-image) blobs are
  capped at 64 MiB.
- The frame reader runs in its own task and is cancellation-safe, so a partial
  frame cannot desync the stream.
- The frame parser and blob reassembly are fuzzed (`fuzz/`, run in CI);
  malformed input returns an error, never a panic.
- Protocol-version skew is caught in the handshake with a clear message; the
  daemon refuses rather than misbehaving.

### Secret hygiene

- macOS: pasteboard items typed `org.nspasteboard.ConcealedType`,
  `TransientType`, or `AutoGeneratedType` (password managers) are skipped
  before the content is read.
- Wayland: best-effort check of `wl-paste --list-types` for a password-manager
  hint.

## Known limitations / non-goals

- **No forward secrecy for pairing metadata:** the identity keys exchanged
  during pairing are long-term; if `identity.pem` leaks, re-pair (`qdrop pair
  --remove`, then pair again — this issues a fresh key on the next daemon
  start? no: the key is persistent, delete `identity.pem` to rotate).
- **mDNS is unauthenticated:** an attacker can spoof discovery records, but
  cannot complete a TLS handshake without a pinned key, so the worst case is
  wasted dial attempts (bounded by backoff).
- **No protection against a fully compromised local machine.**
- **Wayland concealed-content detection is heuristic** — not every password
  manager sets a hint. Prefer `sync_images = false` on shared machines.
- **The 6-digit PIN** is fine for a brief, user-supervised pairing on a home
  LAN; it is not a substitute for a real key exchange over a hostile network.

## Rotating trust

- Unpair: `qdrop pair --remove <name>` (takes effect within ~3 s, no restart).
- New identity key: stop the daemon, delete `~/.config/qdrop/identity.pem`,
  restart, and re-pair every device.
